# ChemUSON 0.3.0-beta.1 — notas de preparación

> **Estado: CANDIDATA EN PREPARACIÓN — NO PUBLICADA.** Este documento no anuncia una descarga. No se ha creado el tag `v0.3.0-beta.1`, una GitHub Release ni se han modificado los canales o `gh-pages`.

## Identidad preparada

- Versión canónica: `0.3.0-beta.1` (`src/chemuson/_version.py`).
- Rama de preparación: `release/v0.3.0-beta.1-prep`.
- Los paquetes oficiales sólo podrán construirse desde el commit revisado/tag validado y con AppStream, instalador y manifests concordantes.
- Para evaluación previa a publicación, usar únicamente los **Actions preview artifacts** documentados en [PREVIEW_BUILDS.md](PREVIEW_BUILDS.md); no son actualizaciones del producto.

## Áreas a evaluar

La candidata contiene el código de la línea 0.3.x existente en el commit seleccionado. La matriz de [aceptación manual](manual-acceptance-0.3.0.md) es la referencia de lo que se ha probado y de los resultados pendientes; no se asume que una capacidad esté aceptada sólo por aparecer en el código.

- Editor 2D, importación/exportación, persistencia `.cmsn`, undo/redo y herramientas geométricas.
- Paneles/análisis y flujos de trabajo 3D disponibles en la versión.
- Molecular Assistant, sujeto a las limitaciones experimentales indicadas abajo.
- Instalación y ejecución desde cada uno de los cuatro paquetes de preview.

## Limitaciones y advertencias

- **Bloqueo P1 de aceptación y publicación beta:** el propietario confirmó que faltan iconos de interfaz en los paquetes portable Windows y Linux del primer preview, en ambos temas. La causa en el build común es que el spec no incluía los SVG estáticos en el ejecutable congelado. El smoke corregido de CI será una condición de build, pero no equivale a aceptación visual: el propietario debe repetir la prueba en los nuevos paquetes Windows y Linux antes de continuar la aceptación o publicar la beta. Estado actual: `FAILED — P1 BLOCKS BETA PUBLICATION`.

- **Molecular Assistant es experimental.** La salida de un modelo requiere revisión química. Una cadena SMILES válida no demuestra por sí sola que la identidad solicitada sea correcta. Disponibilidad, configuración del proveedor y calidad de respuesta dependen de servicios externos; la matriz registra por separado validez, procedencia e identidad.
- **UI-ONBOARDING-001 — retest pendiente.** En el segundo Build Preview el propietario observó el onboarding desalineado en Windows portable. La fuente difiere su creación hasta después del primer layout visible y recalcula el spotlight en resize/move/cambio de pantalla; se conservan los tres pasos y la preferencia existente. Las pruebas Qt no sustituyen el retest en el nuevo paquete Windows (y comprobación de consistencia Linux): sigue `NOT TESTED — owner retest required`.
- **BRANDING-001 — retest pendiente.** Las superficies de presentación del programa se normalizaron a `ChemUSON`; no se han inspeccionado aún los nuevos paquetes Windows/Linux. Sigue `NOT TESTED — owner retest required`.
- **Deuda Qt pendiente.** Una suite monolítica histórica abortó durante teardown con SIGSEGV/exit 139 y existió un reproductor sensible al orden. La causa no se da por demostrada ni resuelta. Los cierres repetidos de ventanas y diálogos son prioridad en las pruebas manuales; un smoke aislado no cierra esta deuda.
- **Linux portable:** la corrección construye un AppImage Type 2 real desde un AppDir y conserva el contrato de updater oficial. Una build Linux local de la corrección pasó firma, extracción, recursos y rasterizado congelado; aún falta el Build Preview remoto y su validación por los runners oficiales.
- No se afirma que la compilación real de los cuatro paquetes haya ocurrido hasta tener una ejecución GitHub Actions completa y satisfactoria. La validación YAML/estática no es evidencia de un build real.
- Clean2D, las reglas químicas y la serialización `.cmsn` no son objeto de cambios en esta campaña. Los casos de aceptación detectan regresiones; no amplían ni certifican todas las heurísticas.
- Authenticode, HMAC y firma GPG dependen de secrets/configuración protegidos; no asumir que un paquete está firmado si la ejecución no lo acredita.

## Antes de cualquier publicación

1. Revisar SHA y procedencia de los cuatro artifacts de Actions.
2. Ejecutar y registrar casos de aceptación en Windows y Linux, incluyendo instalación/actualización, cierre, persistencia y datos químicos.
3. Resolver o aceptar explícitamente cada fallo y deuda; P0/P1 atribuible bloquea stable.
4. Obtener aprobación del propietario, verificar los rulesets y environments de GitHub y sólo entonces decidir si crea el tag protegido `v0.3.0-beta.1`.
