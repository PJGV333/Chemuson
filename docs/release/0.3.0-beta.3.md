# ChemUSON 0.3.0-beta.3 — preparación

## Estado

Candidata de recuperación en la rama aislada `release/v0.3.0-beta.3-prep`, creada desde el commit exacto `6aecba5a5585d9560b693186578b76bea9e623b8` de la candidata beta.2. La versión canónica y AppStream se preparan como `0.3.0-beta.3`; el workflow oficial consume `0.3.0-beta.3-public.md`.

## Por qué existe beta.3

El push del tag anotado `v0.3.0-beta.2` sí inició el workflow oficial (run `40160549763`), pero el job `release_gate` falló en 10 segundos en el paso `Validate immutable tag and exact source SHA`:

```text
Release preflight failed closed: Command '['git', 'rev-parse', 'HEAD']' returned non-zero exit status 128.
```

Causa raíz: `packaging/release/validate_release_tag.py` calculaba `REPO_ROOT = RELEASE_DIR.parents[2]` partiendo del **directorio** `packaging/release`, resolviendo un nivel **fuera** del checkout. En el runner, `git rev-parse HEAD` se ejecutaba en `/home/runner/work/Chemuson` (sin repositorio Git) y el preflight fallaba cerrado. Los scripts compañeros (`set_version.py`, `preview_build.py`, etc.) calculan `parents[2]` desde el **archivo**, que sí es correcto; por eso el Build Preview y las pruebas unitarias auxiliares nunca ejercitaron la constante defectuosa. La corrección es `REPO_ROOT = RELEASE_DIR.parents[1]`.

## Qué incorpora esta preparación

- Corrección localizada de `REPO_ROOT` en `validate_release_tag.py` y regresiones: la constante coincide con `git rev-parse --show-toplevel`, se ejecuta la lógica real de `verify_tag_checkout` y del script completo en un checkout de ensayo con tag anotado.
- Job `Release preflight rehearsal (non-publishing)` en el Build Preview: reproduce el preflight oficial en un runner de GitHub Actions con checkout completo del SHA candidato, tag anotado temporal `v<versión>` creado y borrado **solo dentro del runner**, evento de tag simulado (ref, tipo, archivo de evento, `GITHUB_SHA`, `GITHUB_OUTPUT`), token de lectura `github.token`, verificación de exit code 0 y de las salidas `tag/version/channel/sha`, y salvaguardas `git ls-remote` de que el tag oficial nunca existe ni se publica.
- Job `Release gate bounded checks rehearsal`: replica byte a byte (verificado por contratos) los pasos acotados del `release_gate` oficial tras su preflight, en el mismo runner y con el mismo entorno.
- Ambos ensayos alimentan el `preview_report`: si algo no pasa, el Build Preview completo se declara incompleto (fail-closed).

## Preservación Git

- `v0.3.0-beta.1` (anotado, apunta a `85fa4ed2bd0afe1d31953440228fb73a69b54e7e`) y `v0.3.0-beta.2` (anotado, apunta a `6aecba5a5585d9560b693186578b76bea9e623b8`) permanecen intactos. Sus commits y evidencias no se reescriben.
- Beta.2 no generó GitHub Release ni assets: el workflow falló en el preflight antes de construir nada. No se reintentará beta.2; la recuperación usa la numeración monotónica beta.3.

## Publicación pendiente

Esta preparación no crea `v0.3.0-beta.3`, GitHub Release, assets oficiales ni publicación Flatpak. El propietario debe revisar el SHA exacto de la candidata y la evidencia del ensayo del preflight en Actions, y confirmar expresamente antes de crear el tag. El workflow oficial sigue siendo la única vía de publicación; los artifacts del Build Preview sólo sirven para verificación.
